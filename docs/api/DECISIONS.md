## Facts, conflicts, and proposed design

| ID | Source or discrepancy | Proposed contract and rationale | Impact |
| --- | --- | --- | --- |
| ADR-01 | UCS §6.2.1 p26 requires a protected session. SAD §§4.1 and 4.4, pp18 and 22–24 describe an expiring token sent in a header. | Use an opaque random bearer token over TLS, with a revocable digest stored server-side. Configure absolute expiry, for example eight hours. Keep the token in browser memory and out of URLs and local logs. Logout immediately revokes it. The proposal defines no refresh endpoint. Review storage, hashing, and rate settings during implementation. | Authentication and authorization. Q-05 requires deployment provisioning. |
| ADR-02 | UCS §3, pp16–18 requires authoritative amounts. The team settled currency and rounding in Q-04. | Use VND integers, one unit per dong, with a maximum of 9e12. Calculate percentage discounts in basis points and round once to the nearest dong, half up. Allocate by largest remainder using ascending seatId to break ties. Line payables sum to subtotal minus discount. | Quotes, payment, and reporting. Q-04 and Q-06. |
| ADR-03 | UCS §§3–4, pp16–22 defines PENDING, SUCCESS, FAILED, and EXPIRED. SAD §4.7 p27 uses PENDING_PAYMENT, CONFIRMED, EXPIRED, and CANCELLED. | Map PENDING_PAYMENT to PENDING, CONFIRMED to SUCCESS, and EXPIRED to EXPIRED. Map declines to FAILED and expiry to EXPIRED according to the actual outcome. Showtime cancellation uses a separate flag and expiry reason for pending bookings. Customer cancellation here ends before booking creation. | Booking states and cancellation. Q-03. |
| ADR-04 | UCS §5.2.1 p23 uses UNUSED and USED. SAD §4.9, pp31–33 uses ACTIVE, USED, and CANCELLED and specifies one QR ticket per seat. | Expose UNUSED for SAD ACTIVE and preserve USED and CANCELLED. VALID is a preview result. Two seats receive two tickets, and each ticket is admitted separately. The contract defines no bulk or group QR admission. | Issuance, owner access, and staff admission. Q-02. |
| ADR-05 | UCS §4.2.2.5 p21 covers late success. SAD §§4.8 and 4.13, pp29 and 39 describe transitions out of PENDING. | Preserve the terminal fulfillment status. Record the provider result and reconciliation separately in providerOutcome and reconciliationStatus. Apply guarded local state changes backed by a durable inbox and recovery records. The documented transaction boundary is local. | Late success, mismatches, and unknown outcomes. Q-01 and Q-03. |
| ADR-06 | UCS §§2.3 and 3.3, pp14 and 17 require transactional protection and uniqueness. SAD §4.13 p39 describes database uniqueness. | Scope retry keys to the actor and operation and propose 24-hour retention. The rules for one booking per hold, one logical payment per booking, one ticket per booking and seat, and one admission per ticket outlast the retry cache. Network delivery may repeat. | Mutation retries, error handling, and replay. |
| ADR-07 | UCS §§15 and 18, pp51–53 and 59–61 leave discount rules and conditions partly undefined. | Support a fixed amount or capped percentage in basis points, minimumSubtotal, and allowed movies, showtimes, or seat types. An empty list means unrestricted. Combine configured conditions with AND and require all selected seats to qualify. Allow one code per booking. Stacking and quotas require owner approval. The booking fixes the price after quote revalidation against the latest version. | Q-04 financial policy. |
| ADR-08 | UCS §14, pp49–50 requires SUCCESS plus USED for eligibility and allows a duplicate error or update. Q-06 approves the 1–5 scale. | Use an integer rating from 1 through 5 and optional text up to 2000 characters. Return 409 on duplicates. Publish the arithmetic mean and count without exposing account or booking data. The proposed API has no review update. | Q-06 validation policy. |
| ADR-09 | UCS §9.2.2.3 p36 blocks room or time changes with HELD or SOLD seats and permits cancellation after warning and confirmation. | Read impact counts and issue a token bound to the latest counts and version. Require explicit confirmation. Apply the cancellation guard immediately, then release, notify, and reconcile asynchronously. Queue eligible payments for authorized full refund under Q-03. | Pending and paid bookings affected by cancellation. |
| ADR-10 | SAD §4.4 p23 describes creating and deactivating Staff/Admin. UCS §6.4.2 p27 refers to preconfigured accounts. SAD §4.8 p29 supports administrative payment lookup. | Provision privileged accounts through deployment configuration. Administrative payment lookup remains read-only. | Supporting administration. |
| ADR-11 | SAD §4.7 p27 makes hold TTL configurable. UCS §9.3.1 p36 calls for a cleaning interval, and §12.2.2.5 p45 refers to the current admission window. | Configure hold TTL, cleaning interval, and admission window. Default to 600 seconds and 15 minutes. Apply the approved fixed admission window. | Q-02 and Q-06. |
| ADR-12 | The checkout has no established backend conventions or dependencies. | Use REST JSON at `/api/v1` with OpenAPI 3.1.0 and JSON Schema 2020-12. API_GUIDE.md defines money, ID, time, and filter conventions. STATE_AND_EVENTS.md describes WSS separately. | All documented operations. |

## Additional design decisions and examples

- ADR-13 (PROPOSED) adds public grid coordinates bound to layoutVersion. Clients can render arbitrary labels and aisles from the snapshot. Geometry changes require WSS resynchronization. See UCS §2.2.1 p13 and §8.2.1 p32.
- ADR-14 (PROPOSED) defines update rules for every ShowtimeUpdate field and state. HELD or SOLD seats block movie, category, room, and time reassignment. ACTIVE showtimes cannot return to DRAFT, and terminal showtimes cannot reopen. The explicit warned cancellation path remains available. See UCS §9.2.1 p35 and §9.2.2.3 p36.
- ADR-15 (PROPOSED) uses last successful commit wins for profile edits. They accept only displayName. Admin entity updates use optimistic expectedVersion. See UCS §6.2.1 subflow 3 p26.
- The payment example returns 202 with CREATING and a null checkoutUrl. The two-seat READY example returns both tickets. The report example uses an asOf of 12:01Z, after the 11:45:01Z admission.
- The ten planned acceptance checks list their sources, pass conditions, and proposed environments. Their status is NOT RUN.
